# Kharakteres 정량 평가

고정 주문·질의·정답 라벨을 사용해 검색, 생성, 충돌 검토를 반복 비교합니다. 실제 구현인 `SpellVectorIndex.rank`, `SpellGenerator.compose`, `lexicon.review`, `SpellGenerator.ai_review`를 호출합니다. 사용자 서버·계정 DB는 사용하지 않으며 벡터 인덱스는 임시 폴더에서 생성합니다.

## 현재 평가 체계의 수준

미니 프로젝트에서 개선 효과와 한계를 설명할 수 있는 정량 평가 체계를 갖췄습니다. 고정 데이터·정답표·동일 모델 대조·반복 실행·블라인드 LLM 채점·사례별 실패 기록·독립 재계산을 제공합니다. 평가 방법의 재현성과 서비스 성능의 충분함은 별도 판단입니다.

| 판단 대상 | 현재 판단 |
|---|---|
| 재현성과 검증 범위 | 과제 수준에서 적절함. 같은 고정 입력의 검색·생성·충돌 검토를 비교할 수 있음. |
| 검색·충돌 성능 | 개선 근거와 함께 검색 누락·무정답 오검색·AI 충돌 오탐이 확인됨. |
| 생성 품질 | 이번 데이터에서 RAG 사용에 따른 향상이 확인되지 않음. 형식 통과를 의미 정확도로 해석하지 않음. |
| 일반화와 전문 정확도 | 작은 합성 세트·제한된 언어/무정답 사례·LLM 채점만으로 실사용 전반이나 고전어 정확도를 입증할 수 없음. |

현재 우선순위는 평가 도구를 늘리기보다 검색 실패와 충돌 오탐을 분석하고, dev에서 개선안을 조정한 뒤 새 test 사례로 확인하는 것입니다. 기존 test 결과와 원본 산출물은 비교 증거로 보존합니다.

## 실행

프로젝트 루트에서 실행합니다. 결과 폴더는 새 이름을 사용합니다. 기존 결과는 덮어쓰지 않습니다.

```bash
# 실제 로컬 임베딩 검색 + 규칙 충돌 검토. LLM/API 호출 없음.
.venv/bin/python eval/kharakteres_benchmark.py \
  --tasks retrieval conflicts --repeat 2 \
  --output eval/results/my-local-evaluation

# 동일 모델의 RAG 유무 비교 + 실제 AI 충돌 검토 + 블라인드 LLM 채점
# .env의 OpenAI 모델/키를 사용하며 실제 API 사용료가 발생합니다.
.venv/bin/python eval/kharakteres_benchmark.py \
  --backend openai --tasks retrieval conflicts generation \
  --judge --repeat 2 --max-model-calls 80 \
  --output eval/results/my-openai-evaluation

# Ollama도 같은 명령의 --backend ollama로 비교 가능
# LLM 호출 예산만 같고 소요 시간·모델·성능은 별도로 기록합니다.

# API 호출 없이 결과 누락/중복·라벨·지표·통계 재계산 검증
.venv/bin/python eval/audit_kharakteres_report.py \
  eval/results/my-openai-evaluation/report.json

# 지표 계산·오류 처리·계정 분리 등을 포함한 회귀 테스트
.venv/bin/python -m pytest -q
node --test tests/test_stream_client.cjs
```

첫 실행에는 FastEmbed 모델 파일을 다운로드할 수 있습니다. `fake`는 LLM 선택이며 검색 평가는 이 모드에서도 **실제 ONNX 임베딩**으로 수행합니다. fake 생성 결과는 AI 품질 근거로 사용하지 않습니다. 실제 모델 평가의 기본 trace는 꺼져 있으며 `--trace`를 붙이면 기존 LangSmith 환경 설정에 따라 합성 평가 입력을 추적합니다.

## 고정 데이터와 재현 조건

- `eval/datasets/kharakteres_v1.json`, 버전 1.0.0: 합성 주문 16개, 검색 질의 24개(dev 6/test 18), 충돌 사례 16개(dev 2/test 14), 생성 요청 6개(test).
- 검색에는 동의 표현·복수 정답·다른 세계관·무정답이 있습니다. test의 정답 있는 질의는 17개, 무정답 질의는 1개입니다. 현재 질의는 주로 한국어 의역이므로 다국어 검색 전반을 대표하지 않습니다.
- 충돌은 `(비교 주문 ID, 충돌 종류)` 정답과 `AI 의미 모순 대상 ID` 정답을 따로 둡니다. 동일 효과의 변형·반대 속성만으로는 AI 의미 모순으로 보지 않습니다. 세계관이 다르면 비교 대상에서 제외합니다.
- 생성은 한국어·영어·라틴어·고전 그리스어·산스크리트어 6요청이며, 요청별 의미 기준 3개를 미리 기록했습니다. 정답 주문 문장 하나를 강요하지 않습니다.
- 라벨은 평가 실행 전에 작성한 소규모 합성 정답표입니다. 독립된 여러 평가자의 합의 라벨이나 전문가 언어학 검수가 아닙니다. 정답표 자체도 검토 대상입니다.
- 같은 split·입력·모델·프롬프트·코퍼스를 유지하고 조건 실행 순서는 고정 seed로 섞습니다. 두 조건은 기존 주문 문맥의 유무만 다릅니다. 데이터 SHA256, 모델 이름, Git commit/dirty, 설정, 실행 시각을 기록합니다. 새 실행부터 평가 코드·서비스 코드 스냅샷과 해시, Python·의존성 버전도 기록합니다.
- 기본 검색 `k=3`, 최소 유사도 0.25는 현재 서비스 기본값을 사용했습니다. 생성 문맥은 서비스와 같이 최대 12개입니다. test 결과를 본 뒤 이번 수치를 올리려고 임계값을 조정하지 않았습니다. 향후 조정은 `--split dev`에서 하고 새 test 세트로 확인해야 합니다.
- 반복은 기본 1회이며 이번 실측은 2회입니다. 같은 사례의 반복 평균을 먼저 내고 사례를 재표집해 대응 차이의 bootstrap 95% 구간을 계산합니다(seed 104, 2,000회). 반복 수를 독립 사례 수로 부풀리지 않습니다.

## 비교 조건과 지표

| 대상 | Before 조건 | After 조건 | 측정 |
|---|---|---|---|
| 검색 | 서비스의 기존 AND 텍스트 검색(`lexicon.search`) | 실제 다국어 dense vector + cosine 검색 | Precision@3, 반환 결과 정밀도, Recall@3, MRR, nDCG@3, 무정답 거절 정확도, 세계관 유출률, 지연 |
| 규칙 충돌 | 같은 세계관의 완전 일치 이름만 검사 | 이름·주문문 정규화, 정의 차이, 유사 효과 검사 | 사건 단위 TP/FP/FN/TN·micro P/R/F1·정확도, 사례별 완전 일치율 |
| AI 충돌 | AI 검토 없음(`findings=[]`) | 현재 서비스의 실제 AI 설정 검토 | 대상 주문 ID 단위 P/R/F1·정확도, 사례별 완전 일치율, 오류·토큰·지연 |
| 생성 | 기존 주문 문맥 없이 생성 | 검색한 기존 주문을 문맥으로 제공 | 스키마·요청 메타데이터·제약 문구 보존·발음 항목·문자 범위·원문/이름 중복·작가 입력 보존, LLM rubric·체크리스트 |

여기서 Before는 **Kharakteres 안에서 특정 기능을 제외한 대조 조건(ablation)**입니다. 장애 진단 BASE AI의 과거 답변과 주문 생성 답변을 직접 점수 비교한 것이 아닙니다. `name_only`와 `no_findings`는 명시적인 단순 대조군이며 BASE 원본의 전체 동작을 재현했다고 주장하지 않습니다.

검색의 Precision@k는 `상위 k 내 정답 수/k`이며 k개 미만을 반환해도 분모는 k입니다. `returned_precision`은 실제 반환 개수를 분모로 합니다. Recall@k는 `검색한 정답 수/전체 정답 수`입니다. 무정답 질의의 recall/MRR/nDCG는 null로 두고 평균에서 제외하며 빈 결과 반환 여부를 별도 측정합니다. 공집합에 재현율 100%를 부여하지 않습니다. nDCG는 이진 관련성의 위치 할인 점수입니다.

충돌 `accuracy`는 비교 가능한 사건/주문 쌍을 분모로 합니다. 음성 사례가 많으면 높아질 수 있으므로 F1과 사례 완전 일치율을 함께 봅니다. 오류는 별도 error_rate와 end-to-end 완전 일치 실패로 남습니다. 오류 시 빈 예측으로 산출된 혼동행렬만으로 성공을 주장하면 안 됩니다.

생성의 계약 검사는 형식적 지표입니다. 제약 문자열이 결과에 들어 있다고 의미적으로 지켰다는 뜻은 아니며, 문자 범위·발음 항목 존재도 언어 정확도 인증이 아닙니다. 의미 품질은 아래 평가와 사람이 확인해야 합니다.

## LLM-as-judge와 사람 검토

같은 요청의 두 초안을 A/B로 가리고 순서를 섞어 한 번에 평가합니다. 작성 조건 이름은 평가자에게 보내지 않습니다. 평가자는 `.env`의 fast 모델, 생성은 quality 모델을 사용하며 이름을 기록합니다. 같은 제공자·모델 계열이라 평가 편향이 남을 수 있습니다.

- 지시 준수, 기존 설정과의 일관성, 기존 주문과의 차별성, 표현의 적합성을 각각 0~4점으로 채점합니다.
- 요청별 사전 기준 3개의 충족 여부와 이유를 저장합니다. 각 차원 3점 이상이고 기준을 모두 충족하면 rubric pass입니다.
- 평가 JSON의 점수 범위·정수 여부·기준 개수를 검증합니다. 잘못된 평가 응답은 누락을 숨기지 않고 judge_error와 coverage로 표시합니다.
- `human_review.csv`에는 무작위 A/B 초안과 동일 rubric의 빈 칸을 내보냅니다. 사람이 독립 채점할 때 사용하며 조건 대응표는 `report.json`에 있습니다. 이번 결과에는 사람 채점 점수가 포함되지 않았습니다.

LLM 채점은 객관적 진리나 고전어 검수가 아닙니다. 평가 모델을 바꾸면 이전 LLM 점수와 직접 비교하지 말고 같은 고정 입력을 두 조건에 다시 적용합니다.

## 결과물과 실패 처리

`report.json`은 원본 초안·정답·반환 ID·사례별 점수·채점 이유·혼동행렬·모델 호출 기록을 포함합니다. `cases.csv`는 사례별 수치, `report.md`는 요약과 대응 차이, `audit.json`은 독립 재계산 결과입니다. `source/`에는 새 실행의 재현용 코드 스냅샷이 있습니다. 언어 확장 후 새 실행은 포함 ISO/제공자 자료와 저작권·라이선스 파일도 함께 기록합니다.

사례마다 중간 결과를 저장해 중단 시 부분 결과도 남깁니다. 실행 중에는 complete=false입니다. 실행 오류는 종료 코드 1, 정상 완료는 0입니다. 종료 코드 0이나 audit 통과는 **실험이 온전히 기록됐다는 뜻이며 품질 목표 달성 판정은 아닙니다**. 평가자는 오류·오탐·미탐·무정답 사례를 함께 확인해야 합니다. LLM 호출은 자동 재시도하지 않으며 최대 호출 예산에 실패한 호출도 포함합니다. 어댑터/공급자 내부 재시도 횟수는 계측하지 않았습니다.

임베딩 초기화·코퍼스 임베딩 시간은 index_build_ms로 분리하고, 검색 지연은 준비된 인덱스 기준입니다. 로컬 계산 비용은 미산정입니다. OpenAI/Ollama 어댑터의 USD는 토큰 수×가상 혼합 단가이므로 실제 청구액으로 제시하지 않습니다. 오류 응답으로 사용량이 제공되지 않은 호출 비용도 확정할 수 없습니다.

## 측정 범위와 다음 검증

이 벤치마크는 검색·초안 작성·충돌 검토의 핵심 함수를 측정합니다. 웹 사전·콘텐츠 필터·음성·인증·SSE·UI를 포함한 전체 요청 시간은 아닙니다. 별도 pytest와 컨테이너 스모크로 현재 인증·저장·시크릿·SSE를 확인하고, 외부 어휘 검증·실제 오디오·브라우저 호환성은 각각의 실행 증거와 구분합니다.

작은 합성 세트, 의역 중심 질의, 무정답 1개, 쉬운 생성 요청, 주관적인 LLM judge, 결정적 출력에 가까운 2회 반복은 한계입니다. 정량 장치가 확장됐어도 전체 사용자 성능이 입증된 것은 아닙니다. 다음 데이터 버전에는 실제 사용자가 작성한 질의, 무정답·언어별 균형, 전문가 검수, 혼합 충돌·경계 사례, 블라인드 사람 채점이 필요합니다.

실측 수치와 과제 기준 대조는 [과제 평가 점검](ASSIGNMENT_REVIEW.md), 원본 결과는 [통합 평가 보고서](../eval/results/kharakteres-benchmark-20261021/report.md)를 참고합니다.

## Docker 격리 스모크 재현

사용자 데이터 볼륨이나 .env를 연결하지 않는 전용 검사입니다. 실행 후 tmpfs는 사라집니다. 실제 모델·음성 API는 호출하지 않습니다.

```bash
docker build -t kharakteres:evaluation .
docker run --rm --read-only \
  --tmpfs /app/data:uid=10001,gid=10001,mode=0700 --tmpfs /tmp \
  -e LLM_BACKEND=fake -e CONTENT_FILTER_MODE=rules -e SPELL_VECTOR_ENABLED=0 \
  -e LANGSMITH_TRACING=false -e KHARAKTERES_COOKIE_SECURE=0 \
  -e KHARAKTERES_CONTAINER_SMOKE=1 \
  kharakteres:evaluation python eval/kharakteres_container_smoke.py
```

고정 데이터셋 평가 이후 사전 제공자 분리와 실패 원인 안내를 추가했습니다. 이 변경은 pytest 115개와 실제 Docker의 4언어 출처 조회·저장·Vue 렌더링으로 확인했으며 [출처 기록](WEB_SOURCES.md#실제-검증)을 참고합니다. 기존 정량 평가의 수치·실행 당시 105개 테스트 기록·코드 스냅샷은 그대로 보존했습니다. 이번 추가 검증을 생성 품질 평가나 브라우저 전체 검증으로 확대해 해석하지 않습니다.

## 확장 언어 목록의 검증 범위

한국어 이름이 있는 자연어 229개로 선택 범위를 정리하고 가나다순으로 표시합니다. 사전 제공자 목록 연결은 229개입니다. 확장 후 pytest 143개와 로컬/Docker UI·목록 갱신·3언어 실제 사전·저장을, 별도로 OpenAI의 포르투갈어·핀란드어·히브리어 생성을 확인했습니다. 기존 고정 데이터 평가 수치는 당시 스냅샷의 증거이며 확장 후 모든 언어의 생성 품질을 같은 점수로 재검증한 것이 아닙니다. [자료·범위·결과](LANGUAGES.md)를 참고합니다.


## 현재 서비스 기능 회귀와 실측의 구분

최신 회귀는 **pytest 152개·SSE 클라이언트 5개**입니다. 지원 언어 229개(현대 209·고전 17·사멸 3), 가나다순, 고전 통합, 영구 세션·새 로그인 우선·계정당 활성 세션 1개가 반영됐습니다. 로컬/Docker 독립 브라우저와 실제 컨테이너 재시작을 확인했습니다([현재 검증 도구](../eval/README.md)).

고정 데이터 208개 결과·모델 호출·검색/충돌/생성 수치·원본 보고서의 당시 105개 기록은 그대로 보존합니다. 이후 언어/인증/UI 변경으로 같은 점수가 재검증됐다고 주장하지 않습니다. 현재 Docker 갱신은 `docker compose up --build -d`이며 명시적인 제공자 재정의가 없다면 `wiktapi`가 기본입니다.
