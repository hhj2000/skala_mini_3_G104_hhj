# Docker, 로그인, 시크릿 모드

## Docker Compose 실행

Docker Desktop 또는 Docker Engine과 Compose plugin이 필요합니다. 프로젝트 루트에서 `.env`를 준비하고 세션 서명 키를 설정합니다. 로그인 계정은 최초 실행 뒤 웹 가입 화면에서 만듭니다.

```bash
cp -n .env.example .env
openssl rand -hex 32
```

`.env`에서 서명 키와 사용할 모델 설정을 입력합니다. 기존 `.env`가 있으면 덮어쓰지 마세요.

```dotenv
KHARAKTERES_SESSION_SECRET=openssl_출력값
LLM_BACKEND=openai
OPENAI_API_KEY=실제_API_키
```

그 다음 프로젝트 폴더에서 실행합니다. **명령 앞에 `SPELL_DICTIONARY_PROVIDER=wiktapi`를 붙일 필요는 없습니다.** Compose와 이미지의 기본값이 이미 `wiktapi`입니다. 다만 셸 또는 `.env`에 다른 제공자를 명시하면 해당 값을 사용합니다.

```bash
docker compose up --build -d
docker compose logs -f kharakteres
```

`http://localhost:8100/` 에서 회원가입합니다. 종료는 `docker compose down`, 최신 코드와 화면을 반영하려면 `docker compose up --build -d`를 사용합니다. 계정 정보·영구 로그인 세션·사용자별 주문 DB·FastEmbed 모델 파일은 named volume에 보존됩니다. 새 이미지로 바뀌어도 데이터 볼륨은 유지하며 적용 후 브라우저를 새로고침합니다. 단순 `docker compose restart`는 새 코드를 빌드하지 않습니다. `docker compose down -v`는 계정·주문 DB와 캐시를 지우므로 백업 없이 실행하지 마세요.

포트 변경은 `.env`의 `DOCKER_PORT=8101`로 지정합니다. Compose 설정은 기본적으로 호스트의 loopback 주소에만 공개합니다. 외부 네트워크에 공개할 때는 TLS를 제공하는 reverse proxy, 강한 비밀번호, 방화벽 규칙을 함께 구성하고 `KHARAKTERES_COOKIE_SECURE=1`을 설정하세요. Compose 기본 포트를 공인망에 직접 공개하지 않습니다.

Ollama를 호스트에서 실행한다면 다음을 설정합니다.

```dotenv
LLM_BACKEND=ollama
OLLAMA_BASE_URL=http://host.docker.internal:11434
```

Docker Desktop에서는 `host.docker.internal`로 호스트 Ollama에 접근합니다. Linux Engine 환경에서 이름을 해석하지 못하면 compose 서비스에 `host.docker.internal:host-gateway` 매핑을 추가합니다. Ollama가 해당 연결을 받도록 호스트 방화벽/네트워크도 설정해야 합니다.

## 웹 어휘 출처

Docker는 기본 `SPELL_DICTIONARY_PROVIDER=wiktapi`로 공개 배포 사전 데이터를 조회합니다. 기존 Docker 환경에서 Wiktionary 직접 API가 HTTP 403을 반환한 문제를 재현해 별도 제공자를 연결했습니다. `docker compose up --build -d`로 갱신하고, 이전 실패 주문은 웹 출처를 재조회합니다. 제공자별 최신성·판본 차이와 실제 검증은 [웹 출처 안내](WEB_SOURCES.md)를 참고하세요.

## 로그인

- 로컬과 Docker 모두 같은 계정 가입·로그인을 사용합니다. 첫 사용자 가입 시 이전 공용 주문 DB가 있으면 첫 계정 서고로 복사하고, 이후 사용자는 별도 주문 DB와 벡터 인덱스를 사용합니다.
- 아이디는 영문·숫자와 `. _ -`로 3~32자, 비밀번호는 12자 이상입니다. 비밀번호는 salted PBKDF2 해시로 저장합니다. 중복 확인은 즉시 확인용이며 실제 가입 시 DB unique 제약으로 다시 검사합니다.
- 로그인은 HttpOnly·SameSite Strict 서명 쿠키를 사용하며 서버의 8시간 자동 만료를 없앴습니다. 세션 식별자의 해시를 계정 SQLite에 보존합니다. 쿠키는 400일 수명으로 발급하고 인증된 정상 응답마다 갱신합니다. Docker는 `KHARAKTERES_SESSION_SECRET`을 필수로 요구하며 로컬 생략 시 서명 키를 계정 DB에 보존합니다.
- 아이디 찾기는 가입 이메일로, 비밀번호 재설정은 아이디와 이메일로 확인합니다. SMTP 이메일 인증을 보내지 않는 개인용 편의 기능이므로 인터넷 공개 서비스의 계정 복구로 사용하지 마세요. Docker 기본 포트는 계속 loopback에만 공개됩니다.
- 비밀번호를 재설정하면 해당 계정의 기존 로그인 세션을 폐기합니다.
- 로그아웃 전까지 로그인 상태를 유지하며 브라우저 재실행·서버/Docker 재시작 후에도 같은 쿠키와 데이터 볼륨·서명 키로 복원합니다. 로그아웃은 해당 세션을 DB에서 즉시 폐기하며 비밀번호 초기화는 해당 계정의 모든 세션을 폐기합니다. 쿠키 삭제·400일 이상 미접속·브라우저의 쿠키 정리·서명 키 변경·데이터 볼륨 삭제 시에는 다시 로그인해야 합니다. 이전 8시간 방식의 쿠키는 이번 업데이트 후 한 번 다시 로그인해야 합니다.
- HTTPS reverse proxy에서는 secure cookie를 켭니다. HTTP를 쓰는 loopback 로컬 개발에서는 기본값을 그대로 둡니다.

## 시크릿 모드

화면에서 **시크릿 모드 시작**을 누르면 로그인 계정의 서고와 분리된 빈 임시 SQLite DB와 별도 벡터 인덱스를 사용합니다. 모드를 종료하거나 로그아웃하면 임시 파일과 주문을 폐기합니다. 서버가 정상 종료되면 진행 중인 세션 임시 저장소도 닫고 지웁니다. 로그인과 시크릿 모드 선택은 유지하되 재시작 후에는 **빈 시크릿 서고**로 복원하며 일반 서고를 대신 노출하지 않습니다.

시크릿 요청은 LangSmith tracing을 끕니다. OpenAI/Ollama 등 생성 모델·음성 API에 전송한 내용은 해당 공급자의 정책을 따르며 로컬 시크릿 모드가 원격 처리까지 숨기지는 않습니다. 실제 주문 입력은 외부 모델에 전송될 수 있습니다. Ollama를 로컬로 실행하면 텍스트 생성은 해당 Ollama 서버에서 처리되고, 음성 기능은 설정에 따라 OpenAI API를 사용합니다.

시크릿 임시 DB는 운영체제 임시 폴더의 제한된 권한 디렉터리에 작성됩니다. 전원 강제 차단·프로세스 강제 종료 때 즉시 정리되지 못할 가능성이 있습니다. 따라서 디스크 forensic 수준의 비밀 저장소로 쓰면 안 됩니다. 이 모드는 앱에서 시크릿 종료를 눌렀을 때 기록을 폐기하는 개인용 작업 공간입니다.

## 검증 범위

2026-10-21에 이미지 빌드와 read-only + 임시 /app/data 컨테이너에서 health·가입/로그인·주문 저장·시크릿 폐기·fake SSE를 확인했습니다. 사용자 볼륨이나 외부 모델 API를 사용하지 않은 격리 검증이며 운영 Compose 배포나 컨테이너의 실제 음성/LLM 품질 검증과는 구분합니다. [재현 명령](EVALUATION.md#docker-격리-스모크-재현)과 [기록](../eval/results/kharakteres-benchmark-20261021/container-smoke.json)을 참고합니다.

계정 중복·복구·접근 격리·이전 세션 취소·재시작 보존은 pytest로 확인했습니다. 이 동작 검증이 공개 서비스용 보안 인증을 의미하지는 않습니다.

## 기존 로컬 주문을 컨테이너에 복사

Docker named volume은 로컬 프로젝트의 계정 DB와 주문 DB와 별도입니다. 예전 공용 주문 DB는 첫 계정 가입 시 자동 복사됩니다. 기존 계정 DB를 Docker에 옮기는 경우 `accounts.sqlite`와 `users/` 디렉터리를 백업 후 컨테이너를 중지한 상태에서 `/app/data/`에 복사하세요. SQLite 파일을 실행 중인 앱에 덮어쓰지 마세요.

## 확장 언어 목록

로컬과 Docker 모두 같은 포함 ISO 언어 자료와 `language_catalog.py`를 사용합니다. 별도 다운로드 없이 목록을 표시하고, 웹에서 제공자 목록 갱신 시 `/app/data/language_catalog.json`에 캐시하므로 Compose 데이터 볼륨에 보존됩니다. 읽기 전용 컨테이너에서도 포함 목록은 사용할 수 있습니다. [선택·갱신·검증 범위](LANGUAGES.md)를 참고하세요.

Docker 빌드에서는 하위 폴더까지 `**/*.sqlite`, `**/*.sqlite-*`, `**/*.db`, `**/*.db-*`와 `data/users/`를 제외합니다. 계정·세션·주문 DB를 이미지에 포함하지 않고 실행 시 영구 볼륨에서 생성/보존합니다. 기존 볼륨은 자동으로 덮어쓰거나 삭제하지 않습니다.


## 동일 계정 중복 로그인 제한

한 서버/공유 계정 DB 기준으로 **계정당 활성 로그인 세션은 1개**입니다. 새 기기/브라우저에서 비밀번호 확인 후 로그인에 성공하면 기존 세션을 교체합니다. 실패한 로그인은 기존 세션을 건드리지 않으며 다른 계정도 영향받지 않습니다. 브라우저를 닫아 기존 장치에 접근할 수 없어도 새 장치에서 로그인할 수 있습니다.

SQLite 트랜잭션과 `login_sessions(user_id)` UNIQUE 인덱스로 여러 요청/프로세스가 같은 DB에 접속해도 세션 두 개가 등록되지 않도록 합니다. 기존 다중 세션 데이터는 기동 시 가장 나중에 등록한 세션만 유지합니다. 기존 쿠키는 다음 API 요청부터 차단하고 시크릿 임시 저장소도 기존 요청 종료 후 정리합니다. 화면은 15초마다 또는 탭/창으로 돌아올 때 확인해 로그인 화면으로 전환하고, API/SSE의 401도 같은 방식으로 처리합니다. 서버 재시작 뒤에도 교체된 쿠키가 다시 살아나지 않습니다.

동일 브라우저 탭은 쿠키를 공유하므로 별개 기기로 판별하지 않습니다. 이 기능은 물리 기기 인증이 아닌 **활성 세션 제한**입니다. 로컬과 Docker는 같은 구현을 사용하지만, 서로 다른 DB/볼륨으로 독립 실행한 서버들 사이에는 세션 상태가 공유되지 않습니다.

같은 주문의 오래된 수정본은 기존 버전 검사(409)로 덮어쓰기를 막습니다. 중복 로그인 자체가 DB 손상을 의미하는 것은 아니며, 이번 제한은 동시 사용 혼선을 줄이는 정책입니다. 교체 전에 접수된 생성/음성 요청이 이미 진행 중일 수 있습니다. 주문 생성은 자동 저장하지 않고, 저장/수정/삭제는 비동기 검사나 잠금 대기 후 실제 변경 직전에 세션을 재확인합니다. 시크릿 해제의 세션 교체도 이전 세션 소유권을 확인하므로 새 로그인을 역으로 무효화하지 않습니다.
